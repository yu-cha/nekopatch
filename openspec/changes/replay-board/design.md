# Design

## Context

- 記録は `nekopatch-history-v1`（`{at, n, d, t, h}` の配列）、遊びかけの盤面と「クリア ○ 問」は `nekopatch-v1` にある（判断 ff86）。
- 遊びかけの盤面（`nekopatch-v1` の `P`）には、色のエリアの分け方 `reg`、答えの猫 `cats`、要る手の高さ `level`、選んだ難しさ `diff` がある。クリアすると、記録に盤面の形は残らない。
- 問題は乱数と時間の予算で作るので、乱数の種からは同じ盤面を作り直せない。
- 今配信している版は、記録を 5 つの値だけの形で保存し直す。知らないキーには触らない。
- 「11×11 の盤面」と「記録に備考を書く」は、別のスレッドで扱う。11×11 は 2026-10-23 に保留になった（ナン「今はいい」）。備考は要件を詰めている。どちらも、あとから入れる側が rebase して合わせる。

## Goals / Non-Goals

**Goals:**

- クリアした盤面の形を残し、同じ盤面をもう一度遊べるようにする。
- 今配信している版のタブが残っていても、その版に戻しても、盤面の形を失わない。
- 盤面の大きさは `SIZES` から読み、11×11 が入っても動く。

**Non-Goals:**

- 今までの記録の盤面を作り直すこと。
- 盤面 ID を入力して遊ぶこと。

## Decisions

1. **盤面の形は、別のキー `nekopatch-boards-v1` に、記録の鍵ごとに置く**（判断 490d）。`{"<at|n|d|t|h>": "<盤面の符号>"}`。記録の鍵は `recordKey`（読み込みで同じ記録を見分けるもの）。
2. **盤面の符号**（`src/core/board.ts`）: `reg` を N 進法の数（BigInt）にして、base64url で N ごとに決まった長さで書く。読むときは、文字と長さと値の範囲を確かめる。
3. **盤面 ID**: `${N}:${符号}` の FNV-1a（32 ビット）を fmix32 で混ぜ、上位 25 ビットを、Crockford の base32 の 5 文字にする。画面に出すためだけに使い、同じ盤面かどうかは符号で比べる。
4. **もう一度遊ぶとき**は、符号から `reg` を作り、解をちょうど 1 つ求めて `cats` にし（`solveUnique`。答えが 1 つでなければ遊ばない）、`logicSolve(N, reg, 3).maxUsed` を `level` にする。大きさと難しさの選択を記録に合わせてから、今の「新しい問題」と同じ `setPuzzle` で始める。
5. **もう一度遊んだ記録の判定**（`classifyPlays`）: 記録を並びの順（保存の順＝日時の順）に 1 回だけ見て、`n|d|符号` ごとに何回目かを数える。盤面の形の無い記録はいつも 1 回目。成績の表（`summarize`）は 1 回目の記録だけでまとめる。数十万件でも、1 回の走査で済む。
6. **クリアの画面の比べ**（`compareWin`）: 今回の盤面と同じ盤面の前の記録があれば「もう一度」として、何回目か、前回との差、ベスト、自己ベストかを返す。無ければ、今までと同じ形で、同じ大きさ・難しさの 1 回目の記録とだけ比べる。「クリア ○ 問」は、1 回目のときだけ増やす。
7. **記録の一覧**: 新しい順（`historyRows`）は、前回比と何回目かを 1 回の走査で求め、絞り込んでから新しい方から `limit` 件を返す。盤面ごと（`boardRows`）は、盤面の形がある記録を `n|d|符号` でまとめ、ベストで並べる。どちらも、残りがあるかを返し、画面は「もっと見る」で `limit` を 30 増やす。
8. **保存の順番**: クリアしたら、盤面の形を先に、記録をあとに保存する。盤面の保存に失敗しても記録は残る（その記録はもう一度遊べないだけ）。記録の保存に失敗したら、盤面の形だけが残るが、害は無い。
9. **ほかのタブとの合わせ**: 今の `syncFromStore` で、記録と一緒に盤面の形も読み直す。
10. **読めない盤面の保存データ**は、記録と同じく `SaveStore` が `<キー>-unreadable-<日時>` に残し、読めた分で書き直す。
11. **書き出しのファイル**: `version: 1` のまま、盤面の形がある記録の行に `"b"` を入れる。`parseExport` は、`b` があれば、その記録の大きさの盤面の符号として読めるかを確かめ、1 つでも読めなければファイル全体を読まない。`importRecords` は、記録と同じ鍵で盤面の形を足す（今の値があれば変えない）。「クリア ○ 問」に足す数は、読み込んだあとの記録で 1 回目の記録のうち、今のスマホにだけあるもの。
12. **確かめ用のページ**: `TRIAL_KEYS` に `boards`（`nekopatch-preview-boards-v1`）を足し、`trialStorage` が写すキーにも入れる。
13. **画面**: 記録の一覧の「遊ぶ」は、行のボタンに `data-n`、`data-d`、`data-b`（符号。base64url なので属性にそのまま書ける）を持たせ、一覧の要素で押されたボタンを受け取る（CSP があるので、インラインの処理は書かない）。確かめの文は一覧の上の欄に出し、押したボタンの文字を「もう一度押す」に変える。5 秒たつか、ほかの「遊ぶ」を押したら、確かめをやめる。
14. **「記録を全部消す」は、一番下に置いて 3 回確かめる**（ナンとの合意 2026-10-23 の追加の ⑤）。押す → 注意の文と「本当に全部消す」「やめる」 → ブラウザの確かめの窓（`confirm`。テストでは `AppEnv.confirm` を偽物にする）。窓はページの外の部品なので、画面を続けて触るだけでは OK にならない。

## Risks / Trade-offs

- 今配信している版のタブが開いたままだと、その間のクリアには盤面の形が残らない → 入れ替えの前に、ナンにタブを全部閉じてもらう。形が残らないだけで、記録は消えない。
- localStorage の使う量が増える（1 件につき 50〜100 文字ほど）→ 判断 490d の見直す条件。
- 備考や 11×11 の変更と同じファイル（`index.html`、`style.css`、`app.ts`、`records.ts`）を直す → 先に `main` に入れた側に、あとの側が rebase して合わせる。確かめ用のページ（`preview/`）は 1 つしか置けないので、置く前にほかのスレッドと順番を合わせる。

## Migration Plan

1. 確かめ用の版を置き（`just deploy-trial`）、ナンのスマホの Chrome で確かめてもらう。
2. 了承を得たらアーカイブし、`main` に取り込み、`just deploy` で本物を入れ替える。入れ替えの前に、ナンにねこパッチのタブを全部閉じてもらう。
3. 戻すとき: `gh-pages` を 1 つ前のコミットに戻して送る。`nekopatch-boards-v1` は前の版が触らないので残り、もう一度入れ替えれば、また使える。
