# ecf8 798a の形に組み直し、手元でビルドしたものを gh-pages ブランチから配信する

## 結論

- df3b を置き換える。ねこパッチを、全アプリ共通の標準（798a の TypeScript の雛形、902a のロジックと UI の分離、f92f の手元の検査、adb8 の OpenSpec）の形に組み直す。
  - ロジック（問題作り、理詰めの解き方、ヒント、クリアの記録）は `src/core/`、画面は `src/ui/web/` に置く。
  - 遊び方と見た目は変えない（ナンとの合意 2026-10-21 の 6）。元の HTML の CSS と画面の部品は、そのまま写した。
- 配信は、GitHub Actions を使わない（f92f）。`just deploy` が、`origin/main` を一時的な場所に取り出してビルドし、その結果を `gh-pages` ブランチに積んで送る。GitHub Pages は `gh-pages` の最上位を配信する。
- 確かめ用の版は、`just deploy-trial` で `gh-pages` の `preview/` に置く（https://yu-cha.github.io/nekopatch/preview/ ）。本物（最上位）には触れない。本物を `just deploy` で置き直すと、`preview/` は消える。
- 1 つの HTML にまとめるビルド（382f の `scripts/inline-build.ts`）は使わない。Vite の普通のビルド（`dist/` に HTML と `assets/`）を、そのまま配信する。共有フォルダ `~/git/apps/` にも置かない（df3b と同じ）。

## 背景

- 2026-10-21、df3b で「直す予定が無い」ので検査の仕組みを置かずに公開した。同じ日に、ナンから「クリアの記録を数年残したい」と頼まれ、記録の上限をなくす、書き出しと読み込みを足す、などで合意した（`docs/requirements-agreement-2026-10-21.md`）。df3b の見直す条件（直しや遊び方の追加を頼まれたら、798a の形に組み直すかを決める）に当たる。
- 頼まれた変更は、ナンの何年分の記録を扱う。読み込みで記録を 2 つにしない、壊れたファイルで今の記録を変えない、今までの記録を必ず読む、などを、手で確かめるだけでは、次の直しで壊しても気づけない。
- 先生の方針で、GitHub Actions は使わない（f92f）。382f にも、GitHub Pages に置くなら「ビルドしたファイルを push する手順も要る」と書いてある。
- ナンのスマホは、VM のホストオンリーのネットワーク（192.168.56.10）に届かない見込み。確かめてもらう版は、スマホから開ける場所に置く必要がある。

## 検討した選択肢

- 作り:
  - **798a の形に組み直す**（採用）: ロジックをテストで守れる。記録の読み書き、読み込みの重なりの除き方などを、シナリオごとのテストで確かめられる。組み直しで遊び方が変わるおそれは、元の処理をそのまま写し、問題作りと解き方のテストを置いて抑える。
  - **1 つの HTML のまま直す**: 手早いが、記録を扱う処理を自動で確かめられない。直しが続くと劣化に気づけない。
- 配信の仕方:
  - **手元でビルドして `gh-pages` に積む**（採用）: GitHub Actions を使わずに済む。確かめ用の版を、本物と同じ場所の下（`preview/`）に、本物に触れずに置ける。`main` に取り込んだ後に `just deploy` を忘れると、配信が古いままになるので、手順を CLAUDE.md に書く。
  - **GitHub Actions でビルドして配信**: `main` に取り込むだけで反映されるが、f92f に反する。確かめ用の版を置くには、作業ブランチからの配信を許す設定も要る。
  - **ビルドしたファイルを `main` の最上位にコミットする**: 公開元の設定を変えずに済むが、`main` に取り込むまで確かめ用の版を置けない。毎回ビルド結果の大きな差分がコミットに混ざる。
- 確かめ用の版の置き場所:
  - **`yu-cha.github.io/nekopatch/preview/`**（採用）: ナンのスマホから開ける。本物と保存領域（同じオリジン）を共有するので、別のキーを使い、本物のキーには書かない（ff86）。本物の記録を読んで写せるので、ナンは今までの記録で確かめられ、書き出して控えも作れる。
  - **VM からの一時的なトンネル（cloudflared など）**: 本物と保存領域が分かれて安全だが、VM を動かし続ける必要があり、今までの記録では確かめられない。
- 1 つの HTML にまとめるか:
  - **まとめない**（採用）: GitHub Pages では別のファイルも読めるので要らない。CSP を `'self'` で書け、Worker も別のファイルにできる（`blob:` を許さずに済む）。
  - **まとめる（382f）**: file:// で開けるが、ねこパッチは共有フォルダに置かない。Google Fonts を残すために `inline-build.ts` を書き換える手間が増える。

## 理由

- 記録を何年も残すという目的に対して、記録を扱う処理を自動のテストで守ることが一番効く。
- f92f を守りながら、確かめ用の版をナンのスマホに届けられるのは、`gh-pages` に手元から積むやり方だった。

## 影響・見直す条件

- `main` は、もう配信されない。配信は `gh-pages` から。`main` に取り込んだら、`nix develop -c just deploy` を実行する（リポジトリの CLAUDE.md）。
- 公開元を `main` から `gh-pages` に切り替えた（2026-10-22、`gh api -X PUT repos/yu-cha/nekopatch/pages`）。切り替えの前に、`gh-pages` の最上位に、それまで配信していた `index.html` と `.nojekyll` をそのまま置いた。切り替えただけでは配信が作り直されなかったので、`gh api -X POST repos/yu-cha/nekopatch/pages/builds` で作り直しを頼んだ。配信の中身は、切り替えの前後で同じだった（sha256 で確かめた）。
- 本物と確かめ用は、同じオリジン（`yu-cha.github.io`）の保存領域を共有する。確かめ用のキーの決まりは ff86。
- `just deploy` を忘れることが続いたら、`wt land` の後に自動で配信する仕組みを検討する。
- 先生が GitHub Actions を許したら、`main` への push で配信する形を検討する。
